# 초읽기 핑·타이머 진단 — 2026-10-21

## 결론

핑이 급변하면 가려진 타이머의 기준 시각이 순간적으로 움직일 수 있다. 인공 지연을 올렸다 내린 실험에서 **가림 이후 약0.300초 후퇴/전진**이 각각 재현됐다. 가림 자체가 계산 속도를 바꾸는 코드는 없으며, 일정한 지연에서는 가림 전후의 일괄 가속이 나타나지 않았다.

별도로, 높은 지연에서 정상 정지 요청이 거절되는 문제도 재현됐다. 실제 측정 RTT 중앙값334ms 조건에서 요청 관측 시점의 시각 차이는 약357.9ms였고, 입력은 거절돼 시간 초과로 목숨이3→2가 됐다. 현재 입력 검증의300ms 제한과 일치한다. 이 수치를 모든 접속에 적용되는 고정 RTT 경계로 해석하면 안 된다. 시각 버퍼·프레임·전송 대기가 함께 작용한다.

**실제 사용자의 인터넷 회선은 측정하지 않았다.** 아래는 같은 PC의 Windows 실행본 두 개를 UDP 중계기에 연결한 인공 지연 실험이다. 게임 로직/패키지/네트워크 설정은 수정하지 않았다. 호스트 본인의 타이머는 모든 조건에서 안정적으로 진행했다. AI전처럼 본인이 호스트인 상황의 증상을 원격 핑 문제로 단정할 근거는 없다.

## 측정 결과

Unity6000.3.18f1 / NGO2.13.3 / Transport2.7.3 / 프로토콜41 / 개발 빌드 / 1:1 / 목표30FPS. 각 조건에서 실제 초읽기 한 판을 진행하고, 화면의 서버 기준 경과 시간이 목표에 도달하는 첫 프레임에 기존 UI 정지 함수를 호출했다. 실제 소유자 RPC와 서버 판정·응답을 사용했다.

| 조건 | 추가 편도 지연 | 측정 UTP RTT 중앙값 | 가림 전 진행률 | 가림 후 진행률 | 요청 관측 시각 차이 | 입력 승인 |
|---|---:|---:|---:|---:|---:|---|
| 기본 연결 | 0ms | 32ms | 1.0010 | 1.0000 | 43.0ms | 승인 |
| 일정 지연 | 50ms | 166ms | 1.0009 | 1.0004 | 166.6ms | 승인 |
| 높은 일정 지연 | 150ms | 334ms | 1.0018 | 0.9960 | 357.9ms | 거절·시간 초과 |
| 가림 후 지연 급변 | 50→350→50ms | 167ms | 1.0005 | 0.9999 | 172.1ms | 승인 |

- 진행률은 `타이머 증가량 / 실제 단조 시간 증가량`이다.1.0000이 정상1배속이다. 프레임 경계·시각 동기화의 작은 변동을 포함한다.
- 급변 조건은 타이머가 가려질 때 편도 지연을350ms로 올리고2초 뒤50ms로 복원했다. 애플리케이션 왕복 지연은 최대766.9ms였다. UTP의 RTT는 평활된 값이므로 순간 애플리케이션 지연과 같지 않았다.
- 이때 게임 타이머 경과 약3.331초 지점에서 실제 프레임 시간 대비 **-300.1ms**, 약5.331초 지점에서 **+300.2ms** 변화가 생겼다. 두 시점 모두 이미 가려진 상태였다. 평균 진행률만 보면 이 튐은 드러나지 않는다.
- 승인된 입력의 기록은 제출 시각을0.01초로 반올림한 값과 일치했다. 전송에 걸린 왕복 시간이 그대로 기록에 더해지지는 않았다. 목표를 넘긴 첫 프레임의 약0~0.03초 차이는 별개다.
- 네 조건의 호스트/클라이언트 총2,468개 타이머 프레임을 수집했다. 표시 문자열과 같은 서버 시각으로 계산한 예상 문자열의 불일치는0개였다. 서버 입력 시각 유효 범위의 경계 검사8개도 각 실행에서 통과했다.

## 코드 근거

1. `Assets/Scripts/RouletteView.cs`, `UpdateClock`: 경과 시간은 항상 `NetworkManager.ServerTime.Time - Clock.StartedAt`이다. `HideAfter` 이후에는 숫자를 `••.••`로 바꾼다. 별도의 속도 배율은 없다.
2. 같은 파일의 `StopClock`: 화면과 같은 `ServerTime.Time`을 정지 요청의 시각으로 제출한다.
3. `Assets/Scripts/DuelClockContest.cs`, `Stop`: `sample < now - .3`인 요청을 거절한다. 이 검증은 초읽기/신호등/욕심의 대가에 공통으로 적용된다.
4. 설치 NGO의 `Runtime/Timing/NetworkTimeSystem.cs`: 네트워크 시각을 보정하며 기본 보정 비율은0.01, 강제 보정 임계는0.2초다. 지연 급변 실험의 시각 튐은 이 시각 동기화 흐름과 일치한다. 가림 처리가 보정을 직접 호출하는 것은 아니다.

## 범위

각 조건 한 판의 진단이며 여러 회선/장시간 통계는 아니다. 패킷 손실/최대6인 부하/전용 서버/실제 인터넷 회선의 지연은 이번 결론에 포함하지 않는다. 요청 시각 차이는 같은 프레임에 함께 전송한 관측 패킷의 서버 수신 시각이며, 실제 정지 RPC와 채널별 도착 차이가 있을 수 있다. 입력 승인 여부와 최종 기록·목숨은 실제 게임의 서버 결과를 사용했다.

따라서 **일정한 낮은 핑에서는 숨김 후 가속을 재현하지 못했지만, 지연 급변에 따른 시각 튐과 높은 핑에서의 입력 거절은 확인했다.** 실제 증상이 발생한 플레이어가 호스트인지 원격 참가자인지, 당시 지연이 급변했는지가 다음 구분 기준이다.
